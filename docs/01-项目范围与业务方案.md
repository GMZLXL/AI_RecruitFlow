# 01｜项目范围与业务落地方案

## 1. 背景与痛点

现有 HR 工作通过企业微信、企业微信群、腾讯在线文档开展；候选人资料和阶段更新散落于对话中，HR 反复打开消息、复制字段、定位表格行、统计进度，造成低效、延迟、遗漏与重复。

## 2. 产品定位

AI RecruitFlow 是一个轻量招聘运营系统：以企业微信自建应用和 Web 管理端为入口，DeepSeek 处理自然语言，FastAPI 负责受控业务操作，SQLite/PostgreSQL 负责可靠记录，腾讯文档智能表格负责协作视图，React 前端提供可视化和审核界面。

## 3. 核心目标与指标

| 目标 | MVP 目标（试运行验收值） | 说明 |
|---|---:|---|
| 结构化抽取字段准确率 | ≥95% | 预先标注的脱敏测试集，按字段计数 |
| 明确唯一匹配的事件自动处理成功率 | ≥90% | 不包括主动要求人工确认的异常事件 |
| 消息->本地业务记录 P95 | ≤10秒（目标） | 取决于模型延迟，非承诺 |
| 消息->腾讯文档 P95 | ≤60秒（目标） | 以授权/接口可用为前提 |
| 平均人工台账操作耗时 | 较基线减少≥70% | 试运行同类工作量对比 |
| 错误自动覆盖已有记录 | 0次 | 多候选人匹配必须进入确认 |

## 4. 一期 MVP 范围

1. 企业微信应用主动投稿、Web端人工粘贴输入；微信群内容通过转发而非后台偷读。
2. DeepSeek 意图识别 + 字段提取；自动识别新增候选人、更新阶段、安排面试、查询待办、周报请求。
3. 唯一申请编号匹配、重复事件去重、歧义确认和状态合法性校验。
4. 应用记录增删改查（删除采用软删除或权限限制）、面试计划、操作审计。
5. 异步腾讯文档智能表格同步（可用/不可用状态明确）、手动重试、死信异常告警。
6. 数据看板：岗位进度、招聘漏斗、待办数量、周度变化。
7. 招聘待办提醒、面试结果未反馈提醒、同步异常提醒。
8. Web 管理端：总览、候选人、申请详情、AI审核队列、待办、同步与设置。

## 5. 二期/不在范围

- 企业微信群全量聊天信息采集（需会话存档能力、企业审批和合规评估）。
- 自动简历评分、自动淘汰/录用；OCR、语音识别、电话外呼与视频面试。
- 双向在线协同编辑与腾讯文档变更合并（需单独技术调研）。
- 多租户计费、复杂审批流、统一身份SSO、完整 ATS 全功能替代。

## 6. 业务操作路径

### 6.1 新增候选人
HR 输入“新增李四，Java开发岗，来源Boss，负责人小王” -> 消息解析 -> 匹配候选人 -> 创建 candidate 与 application -> 数据写入成功 -> 事务内创建 sync_outbox -> 同步腾讯文档 -> 返回结果。

### 6.2 更新面试
HR 输入“A10001一面通过，周五15:00二面” -> 抽取字段 -> 解析时间（不明时区或歧义则待确认） -> 校验申请记录与当前状态 -> 新增 interview/event -> 更新 application 当前阶段 -> 同步腾讯文档 -> 生成待办。

### 6.3 异常处理
同名同岗或缺唯一编号 -> 返回候选申请列表（含非敏感辨识信息） -> HR 在 Web/企微确认 -> 才执行更新。模型“置信度”只是提示，不能单独决定是否提交。

### 6.4 招聘分析
负责人进入招聘看板 -> 选择时间/岗位/负责人 -> 查询本地关系库作准确统计 -> 生成前端图表。AI 周报只负责措辞和观察，不修改原始统计数字。

## 7. 数据口径

- 人：candidate（自然人维度）；申请：application（人×岗位申请实例）；面试：interview（可多轮）
- “新增申请量”以 application.created_at 计；“候选人数”以 distinct candidate_id 计。
- 面试通过率=指定轮次通过人数 / 指定轮次已有结果人数。
- Offer接受率=接受 / (接受+拒绝)，排除尚未给答复的 Offer。
- 招聘周期=录用确认时间-申请创建时间（天），必须指明统计样本和时间区间。

## 8. 成功标准

系统在零第三方凭证下可运行 Mock 端到端；在用户提供授权的测试账户后能完成一条真实智能表格新增、修改、查询闭环；重复消息不重复写；冲突进入确认；日志可追溯；经理不越权查看敏感个人信息。
