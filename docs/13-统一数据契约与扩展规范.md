# 13｜统一数据契约与扩展规范

## S5 增量

schemas/wecom.py定义InboxRead、NotificationRead、ReminderPolicyRead/Update、WecomStatus/Binding/User、MockMessage/TaskRetry。provider(mock/wecom)、投递状态和版本由后端定义并生成TS；凭证不进入API字段。普通响应统一信封，平台回调为text/plain特例，OpenAPI明确XML body。真实wecom source仅通过验签入口，Web不可伪造。

接收、通知和提醒为独立实体，不复用申请stage。provider与事件键创建后固定，accepted不代表已读，Mock有明确前缀。延迟处理内部传入原接收时点，不开放客户端覆盖reference_time。新增列和索引用0005_s5迁移，网络字段仅位于适配器。

## S3 目录与契约增量

S4：独立Offer实体不混进Application.stage，新增事实有独立version/迁移/写入协议；接受与录用不能互相推断。读取工作台/待办/历史/选项集中在schemas/workbench和services/workbench；ApplicationRead新增安全派生字段而不增加冗余业务列。外部投影仅加可空offer_status，旧schema_version=1快照仍可读，provider字段映射继续隔离。

前端所有筛选与实体类型从生成operations/components提取；日历输入集中转换成上海午夜半开UTC区间，时点输入集中带+08:00，页面不另写协议。新增字段须先更新Pydantic/迁移，再生成契约、适配投影和相关表单；测试阻止旧请求覆盖新筛选和错误状态吞掉用户输入。

新增ApplicationProjection（schema_version=1），将业务快照与provider字段映射隔离。外部字段扩展仅改投影构建及适配器映射，不散落到业务路由。任务读取新增provider/mode/internal_only、revision、错误码与重试时间；前端继续生成类型，业务version和任务revision不可混用。

同步派发改为202 accepted，后续通过任务列表读取；请求接受不等于外部成功。腾讯状态为凭证/Schema阻塞，无实测不返回connected。历史任务provider默认mock并固定，新任务才使用显式配置；不能通过环境切换把历史Mock数据导入真实系统。

## S2 目录与契约增量

统一源已分为schemas/common、identity、recruitment、ai、integration模块，由schemas包统一导出。API不再堆入main.py；前端分页面/功能/API目录，生成类型仍是唯一跨语言来源。新增Extraction/ScheduleProposal、接入查询、确认读取/处理请求/结果模型；审核表单类型从生成类型组合，不另写一份业务协议。

S2迁移让结果-only面试的计划字段可空，读类型明确为string|null，安排请求仍必填。接入租约是内部字段，不回显处理token。审核只接受强类型correction与显式目标ID/版本，拒绝任意工具JSON。根路径由core/config集中提供，迁移head自动发现，新增字段不需手改启动版本号。

## S1 落地更新

现已使用UUID数据库主键、Alembic、独立Candidate/Position/Interview及统一UTC类型。ApplicationCreate支持ID引用或便捷姓名/标题的互斥分支；ApplicationRead保持既有字段名并新增owner_id/source_channel/outcome/custom_fields。请求白名单为强校验，前端类型继续由单一契约生成。

CustomFields当前注册organization.referral_tag，值为1~120字符字符串；Candidate和Application使用JSON列。新增组织字段先注册类型与允许的实体，再生成契约；核心业务字段仍新增明确列及迁移。没有开放任意JSON或权限字段注入。补充idempotency_records表用于请求哈希/响应复用，不存原始文本。outbox快照包含schema_version=1及entity数据，实体类型不冒充外部腾讯字段协议。

以下保留S0制定的设计原则与分阶段计划；其中S1目标现已落地，S2/S3功能仍按阶段推进。

## 契约来源与实施范围

先确定结构，再编写接口和页面。唯一运行时契约源为 `backend/app/schemas/` 中的 Pydantic 模型。FastAPI 导出 `contracts/openapi.yaml`，再生成 `frontend/src/types/api.generated.ts`。生成文件禁止手改；根目录 `npm run contracts:check` 检查漂移。未实现的目标接口保留在 docs/05，不能混入当前运行契约。

S0 仅落地已有 Mock 链路的结构；S1 按以下边界补齐实体、数据库迁移与权限，不提前宣称完整 CRUD 已交付。

## 跨语言规则

- JSON 字段使用 snake_case；标识符始终是不可解析的字符串，与申请业务编号 `application_code` 分开。S0 数据库仍为整数主键，在输出边界转字符串；S1 改 UUID 时前端不变。
- 时间使用带时区的 UTC ISO8601（`Z`）；浏览器按 `Asia/Shanghai` 展示，数据库迁移负责 SQLite 的时区恢复与 PostgreSQL 兼容。日期范围为 `[from,to)`。
- 成功使用 `data + request_id`；列表增加 `pagination(page,page_size,total)`；错误使用 `error(code,message,details) + request_id`。请求校验错误不回显输入原文。
- 请求和响应模型分开；请求禁止未知字段，防止拼写错误和越权赋值。响应可增加可选字段，客户端只读取所需字段。核心枚举由 schema 生成，不能在页面另造状态。
- 所有可修改实体保留正整数 `version`。S1 PATCH 必须有 `If-Match`，更新采用数据库条件更新；禁止前端传入 owner/role 等字段绕过权限。

## 领域边界与稳定字段

| 实体 | 核心字段 | 关系/扩展方向 |
|---|---|---|
| User | id, display_name, role, active | 服务端解析身份；角色 HR/MANAGER/ADMIN |
| Position | id, title, department, target_headcount, owner_user_id, active | 岗位独立，不以标题充当关联键 |
| Candidate | id, display_name, created_at, deleted_at | 人的身份与申请分离；联系方式单独授权、加密，不放通用列表 |
| Application | id, application_code, candidate_id, position_id, owner_id, source_channel, stage, outcome, version, created_at, updated_at | 候选人可有多条申请；S0 读取投影保留 candidate_name/position_title；position_id 在 S1 填充 |
| Interview | id, application_id, round, scheduled_at, status, result, feedback_at | 面试结果独立于申请阶段，不把“一面通过”写成“二面通过” |
| IngestionJob | id, source, external_event_id, state, extracted_json, error_code, received_at | source+外部事件 ID 去重；相同文本不代表相同事件 |
| Confirmation | id, ingestion_id, reason, candidates_json, proposed_json, status, resolved_by, resolved_at | 只能处理一次，确认时重新验权限和版本 |
| RecruitmentEvent | id, application_id, actor_id, source, event_type, before_json, after_json, created_at | 结构化事实，不存密钥/完整联系方式 |
| SyncOutbox | id, entity_id, version, status, attempts, next_retry_at, last_error | 每个实体版本一项；provider/mode 与业务状态分离 |
| RemoteRecordLink | id, entity_id, provider, remote_table_id, remote_record_id, last_synced_version | 外部字段映射仅位于适配器 |
| Reminder | id, application_id, reminder_type, due_at, status, dedupe_key | 去重与提醒时区 |
| AuditLog | id, actor_id, action, target_type, target_id, metadata_json, created_at | 与业务/outbox 同事务，网络调用在事务外 |

S0 API 申请投影固定使用 `application_code / candidate_name / position_title`，不沿用 Starter 中模糊的 `code / name / position`。S0 创建申请使用姓名和岗位标题的便捷输入；S1 增加候选人/岗位 ID 输入分支，保留此便捷方式或以新接口替代并明确弃用期，不能静默更改含义。

## 新增字段流程

1. 判断归属：人员资料放 Candidate，岗位放 Position，面试放 Interview，申请进度放 Application。前端读取投影由后端组装，页面不依赖数据库表结构。
2. 需要检索、统计、约束或权限控制的字段：新增类型明确的 schema 字段、数据库列与 Alembic 迁移（可空或有合理默认值），随后生成契约和 TS 类型。只修改使用该字段的表单/视图，不复制接口类型。
3. S1 需要组织自定义字段时，引入实体级 `custom_fields` JSON，键形如 `organization.referral_tag`，配置字段字典，限制类型、大小与访问权限。S0 **暂不接受或存储**任意扩展字段；不使用 `extra=allow` 或宽泛字典代替核心建模。
4. 修改字段类型、删除字段或改变含义属于破坏性变更，使用新字段并提供迁移/弃用说明，必要时升级 `/api/v2`。添加枚举值须检查状态机、标签与生成类型。
5. outbox 在 S3 使用版本化的结构化快照；外部字段 ID 和 provider-specific 数据只存在映射配置/适配器，不传播到前端领域模型。
